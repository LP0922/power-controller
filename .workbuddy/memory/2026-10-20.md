## 1500 RPM 测试：发现实际速度天花板 ~1000 RPM
- 用户要求试 1500 RPM。命令帧被接受（01 F6 ... 02 6B 成功应答），但 0x35 读回实际转速仅 ~58–97 RPM。
- 应答格式修正（手册 p47-48 核实）：0x35 读转速应答 = 地址+0x35+符号(1B,0正1负)+转速(int16)+6B，共6字节，转速在 r[3:5] 而非 r[2:4]；0x36 读位置应答 = 地址+0x36+符号+位置(int32, 0-65535=一圈,多圈累计)+6B，共8字节（此前按6字节读截断）。
- 阶梯测速结果：200→200 ✓、500→499 ✓、1000→1004 ✓（精确跟随）；1500→76、2000→76、3000→55（断崖式掉速）。结论：速度命令通道完全正常，电机在 1000–1500 RPM 之间存在物理上限，最可能是供电电压不足（反电动势顶满母线电压），非协议/驱动代码问题。状态标志 03 无堵转位。
- 位置累计 ~19.8M counts ≈ 302 圈（含昨日失控圈数）。
- 对加粉项目影响：给料速率用不到 >1000 RPM，慢加段反而需要 <100 RPM 精细控制（0.1 RPM 档），此上限不影响控制方案；若确需高速需提高供电电压（待确认当前供电电压规格）。

## 17:27–17:34 MD30 持续超时的三重根因 + 修复（2026-10-20）
用户报错序列：`MD30 response timed out` ×3 → `广播下发后无法读取双机状态，已急停双机` → `MD30 communication failure limit reached`。

**根因 1（致命，纯软件 BUG）：熔断永不复位**
`MD30ModbusRTU._transact` 原逻辑：`if _consecutive_failures >= max(3): raise`。而唯一清零路径是 `_transact` 的成功分支——熔断后永不尝试通讯，就永不成功，于是**永远卡死，只能重启进程**。这就是用户看到 "failure limit reached" 后一直不变的原因。阈值 3 也过小：一次 `_read_positions_with_retry(attempts=3)` × 2 台 × retries=1 就能打满。
修复：`max_consecutive_failures 3→8`、新增 `recovery_cooldown_s=1.5`；熔断后冷却期满**自动清零并放行一次探测**，成功即恢复、失败重新累计。加 `tripped` property。

**根因 2：一次超时就重开串口，形成恶化正反馈**
`app.py poll_status` 里 lift 读失败**无条件** `_reset_bus10()` → 关闭并重开 COM10。USB-485 每次重开都会拉 DTR/RTS 并清空缓冲，从站短暂失联 → 下一轮又超时 → 又重开。偶发超时被放大成持续失联。
修复：新增 `MD30SerialError(MD30CommunicationError)`，只在 `OSError`/串口级故障时重开句柄；"从站没应答"只重试不重开。stir 同理。

**根因 3（未解决，需用户决策）：速度 5 让 MD30 走不动**
日志实证（17:30:50 / 17:30:56 两次对齐）：中点 184 → 实到 188/174；中点 181 → 实到 186/174。**一台只走 2、另一台完全没动，两台都没到中点**。同一套代码速度 10 时（17:19–17:21）六次移动全部到位、偏差 1–4。17:26:50 的 165 报"广播未生效"、17:30:28 的 531 走一点就停，都符合。结论：**速度 5 低于 MD30 本负载下可稳定运行的下限**，导致对齐永远无法收敛、偏差卡在 12–19（贴着容差 20）。

**顺带修复**
- `_read_positions_with_retry` / `read_positions` 改为**逐台独立读取**：原来第一台失败整个列表推导就抛，第二台根本不读，且看不出是哪一台坏。错误信息现在形如「从站1(...)；从站2(...)」。
- 异常消息统一带从站地址：`MD30(从站 1) response timed out`。
- 急停读位置 `attempts 3→1`、起跳监督 `attempts 3→2`：通讯抖动时别让电机在"状态不明"下多跑几秒。
- status 新增 `lift_link`（每台 failures/tripped），页面可判断是哪台不回话。

**离线验证**：死串口连打 → 第 5 次调用触发熔断（计数 8）→ 0.41s 冷却后自动放行探测（不再永久卡死）；双机错误信息正确区分从站 1/2。

**澄清**：日志显示 17:34:17→698、17:34:35→991 两次推杆定位都是**用户自己点的**，不是设备自走。LA error 位在 0/8/12 之间抖动属已知误报（bit3 在电流 0 时误触发）。

## COM10 僵死后只能重启进程的真因：异常类型被包掉（2026-10-20 18:43）
现象：18:09:42 起两台都读不到，先 `response timed out` → 转 `WriteFile failed (PermissionError(13,'拒绝访问'))`，直到 18:42 手动重启才恢复，中间 7500+ 次失败、日志刷了 2.5MB。

**改动**：
1. 两个读取方法内部记录 `serial_broken`，只要有任一台是串口级异常就改抛 `MD30SerialError`（其子类，向上兼容）；纯超时仍抛基类，绝不误重开句柄。
2. 重试循环遇到 `serial_broken` 立即 `break`，不再白等 3 轮超时。
3. 看门狗 `_watchdog_loop` 捕获到串口级异常时也调 `_reset_bus10()`（页面不开时没有别的线程复位 COM10）。
4. 看门狗异常日志节流：同一错误 10s 记一条，恢复时记一条"此前连续失败 N 次"。避免僵死时 0.25s/条把有效日志埋掉。

**离线验证**：mock driver 抛 OSError(13) → 抛 MD30SerialError（判定需重开=True）；抛 MD30CommunicationError('response timed out') → 仍为基类（判定需重开=False）。真机重启后 ok=true，双机 256/249 偏差 7，failures 全 0。

**遗留风险（已告知用户，未改）**：运动过程中若位置读不回来，看门狗只累计到 20 次（约 5s）才报"同步保护失效"，这 5s 内双机在跑且偏差不可见、也不停机。建议改成"上一轮已知在动 + 连续 3 次读不到 → emergency_stop_both()"，等用户确认后实施。
